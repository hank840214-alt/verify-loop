# verify-loop 方法

給指揮 AI（Claude Code、Codex、Gemini CLI）寫程式、但自己不看程式碼的人。你審不了程式碼，所以要讓系統審。

兩位講者沒有審閱或背書本文件；錯誤由我們負責。

兩場演講的兩個想法：
- **限制 AI 碰得到什麼**（參考 [Lydia Hallie 的演講](https://youtu.be/vlfCjWuv4es)）：權限依「做錯能不能救回來」決定，其餘關進沙盒，hook 要真的擋。
- **把修正往金字塔下層推**（參考 [Lauren Tan 的演講](https://youtu.be/O_zcc6Xl12g)）：在最便宜、又能讓錯不再發生的那一層修。其他都抓不到時，才寫文字規則。

Lauren Tan 的倒金字塔（便宜、可信的在前）：程式碼設計 → 靜態檢查（型別、lint、編譯、測試、CI）→ 驗證（操作真 app；狀態與時序用形式化模型）→ 文字規則 → 人工審查。

## 一、出錯時依序問
1. **是授權不是錯誤？**（誰能部署、誰能合併）→ 用 deny 規則或分支保護強制；`AGENTS.md` 只記錄由誰決定。只寫在 prompt 裡沒有強制力。
2. **做錯救不回來？**
   - 永遠不准 → deny 規則＋OS 沙盒。Codex 只透過 `tools/codex-dispatch.sh` 執行。`sandbox.excludedCommands` 不放 AI 啟動指令、`osascript *`、`docker *`：被排除的指令在沙盒外跑，排除不是安全邊界。
   - 有條件才准（剛備份完才能遷移資料庫）→ 腳本前置檢查，不符就拒絕。
3. **機器判得出對錯？** 把金字塔當修正樹走（這是我們依 Lauren Tan 金字塔的整理），停在第一個做得到的，並寫一行「上一層為什麼做不到」。設計時假設下一個 AI 只看它打開的檔案、照抄最近的例子、走最短能過編譯的路：
   1. 改設計讓錯不可能（禁掉 API、資料夾邊界、import 禁令、檔名約定）；同一份狀態只有一個擁有者，手動同步的清單改成單一來源，刪掉會被照抄的舊做法與死程式。
   2. 型別。
   3. lint，錯誤訊息直接寫修法。舊寫法少 → 同一次改動清掉；很多 → lint 只擋新增的，另開一次改動清舊的（§3：先擋新的）。
   4. 測試，驗結果與不變量，不驗程式長怎樣。既有測試在行為壞掉時還會過、或只改內部就會失敗 → 另開一次只改測試的改動，修掉或刪掉。
   5. 功能地圖裡操作真 app 的步驟。
   每個新檢查都要證明：放回真實舊錯會失敗，拿掉後通過。本機和 CI 跑同一條指令。單獨跑兩次並計時；被中斷的執行不能在 repo 留下檔案。
   - **狀態與時序**（多裝置、多人房間、重連、排程、付款）：一般測試抓不到交錯情況。用 TLA+ 建模，把關鍵性質鎖成 repo 檢查，畫成狀態圖給人看。純演算法不變量考慮 Lean。每個專案先挑一條流程；模型要跟程式同步，不同步就刪。
   - **已有文字規則卻又犯** → 算第二次犯。同一次改動往上一層修；文字規則擋不住。
   - **口味**（字太多、像 AI）→ `DESIGN.md`＋截圖、影片、試聽。
4. **只是某件事的做法？** → skill 或腳本。專案規則放 repo，每個 AI 都看得到。

Hook：檢查失敗一定 `exit 2`（exit 1 會被當成完成）。hook 逾時＝沒檢查，所以停止 hook 自設低於 hook timeout 的總時限。失敗或沒跑完，同一個確切狀態只擋一次；之後 Claude 可以收工，並看到 NOT VERIFIED。每次判定都追加到 `~/.claude/state/stop-verify/ledger.tsv`（只在本機、不含路徑）。有子代理、workflow 或 `codex-dispatch.sh` 在跑時先不檢查，等下一次收工再跑。hook 自己壞掉（沒有 `jq`）就 exit 0 加提醒，不卡住 session。

## 二、誰看什麼
- 人只看**成品**：前後截圖、短片、狀態圖、「修前失敗、修後通過」紀錄。用功能地圖的固定名稱溝通。
- **證據規則**：每個「做好了／通過了」都附指令＋輸出，或成品路徑。沒有證據＝沒做完。
- **出題的不改考卷**（來自讀者留言）：同一個 agent 寫修法又寫測試，等於自己出題自己改。
  - 會失敗的測試由「不是寫修法的那個 agent」寫，先單獨 commit。沒有工具檢查是誰寫的；審查者用 `git log` 確認測試 commit 在前、且單獨一個。
  - 修法的改動不准改判它對錯的既有測試。停止 hook 的「測試守衛」會擋（未提交的程式和既有測試一起改 → exit 2；已提交的由證據腳本列給審查者）；新增測試檔可以。測試真的錯 → 另開只改測試的改動，由另一個 agent 或人核准。
  - 證據綁 commit：PR 的驗證段由 `tools/verify-evidence.sh` 產生（commit SHA、指令、結束碼、log 雜湊；加 `--tests-re <測試路徑>` 時列出有沒有動到既有測試），不是 agent 自己寫；審查者核對 SHA＝PR 最新 commit。
  - 合併要人或獨立審查者對同一個 SHA 放行。本機守衛防失誤、不防故意繞過；硬擋要 CI＋分支保護，並把測試資料夾列進 `CODEOWNERS`，動到測試的 PR 一定要負責人審（AI 要用另一個帳號 push）。
- 依風險分級（改編自 Lydia Hallie：一般改動一人審、高風險兩人審）：文案／文件＝檢查綠燈即可；一般改動＝一次審查（不是寫的那個 session）；錢、登入、商店送審、刪資料＝兩道獨立審查＋能退版或關旗標。有懂程式的人時，他算其中一道。

## 三、刪規則
程式註解也算文字規則，AI 會照抄。Lauren Tan 演講中，一個 `setTimeout` 繞路寫法長成 183 個計時器；她的「註解是負債」投影片顯示註解從 65,824 降到 1,227。先用 lint 擋白名單以外的新註解。規則變成測試或腳本後刪文字版；同一件事只留一處；刪掉寫給舊模型的指示（Lydia Hallie）。先擋新的錯，再清舊程式：AI 會照抄現有的東西。

## 四、每週兩個數字（`plans/FINDINGS.md`）
1. 重複：審查發現中同類再出現的次數。應下降。
2. 介入：每件任務人被叫來幾次（核准、貼指令、回答問題）。這個數字下降，才是真的放手。

## 五、導入順序（從第一個缺的開始）
1. 能跑的測試＋CI。
2. 停止 hook 跑測試、失敗 exit 2。
3. deny 規則、可行時開沙盒、Codex 走派工腳本。
4. `AGENTS.md` 授權段、`DESIGN.md` 口味段、功能地圖。
5. 開始記發現帳本。
6. 之後拿一件比平常大很多的任務試跑，記下你在哪幾步被拉回來。那幾步就是下一個要補的檢查。

不要自動化爛迴圈（Lauren Tan）：先做到「AI 寫好程式、AI 自己驗」。前四步沒完成前，不開夜間或總管模式。
